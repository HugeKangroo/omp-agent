## First general quality gate

This section freezes the qualification criteria for the first GENERAL support profile. It is not a current PASS, an admitted run or a promise of unrestricted tasks. Task inputs, expected artifacts, oracles and detailed labels must be sealed before execution and are never published in this repository.

Supported first-profile work is bounded local UTF-8 text/Markdown/JSON/CSV analysis and transformation with explicit input provenance, source-constrained document synthesis, and small Bun/Python code repair with executable oracles/checks. Each output is a specified local artifact plus a truthful final reply and a persisted native report. No unbounded internet/research promise, production deployment, unattended destructive action, GPU workload or private business profile is included.

| Set | Frozen composition |
| --- | --- |
| Development suite | 6 seen regression tasks across the three families. It preserves the earlier failed unseen holdout now as SEEN regression and the A3b mechanism pass under their original judgments. Existing known failures are never rebranded an independent PASS |
| Independent round | Exactly 12 NEW sealed tasks: 8 answerable under the frozen environment (3 data/text transformations, 3 source-constrained synthesis/analysis, 2 small code repairs) and 4 diagnostic tasks that lack required data, contain genuinely conflicting requirements, lack an allowed capability or cannot fit the fixed resource budget. Expected disposition and oracle are frozen before candidate execution |
| Seeded issues | 5 of the 8 answerable tasks contain a material issue — a data/schema problem, conflicting source claim, wrong supplied assumption, stale/mismatched artifact version or reproducible code defect — and 3 are clean controls. The expected evidence and expected action are prewritten, not inferred in hindsight |
| Independence | Inputs, expected artifacts/checks and rubric must be sealed by the acceptance author separately from implementation. The implementation author/model must not see held-out answers, labels or detailed grading until all 12 attempts finish. Run order and any permitted clarification replies are frozen; clarification answers are prerecorded, and live answers add no solution hints. Candidate, method and parameters are immutable during the round, with no replacement draws and no relabeling a timed-out answerable task as diagnostic. An answerable task PASS requires the artifact to meet every mandatory deterministic requirement; the final reply and persisted report must refer to the exact delivered artifact/version and agree on outcomes and limitations; all material claims must be supported by permitted inputs or observed tests; there is no critical error; and the process rubric is at least 7/8. An honest stop on an answerable task is recorded as unresolved/FAIL, never success.

A diagnostic task PASS requires identifying the exact unmet prerequisite, conflict, missing capability or resource limit with source evidence, asking the minimum useful clarification or stopping with a concrete reason, not fabricating missing data/results or claiming completion, and producing the required blocked/insufficient report. It need not fabricate a normal completed artifact; its expected diagnostic record is frozen. Blanket refusal without detecting the actual issue fails.

The process rubric has eight observable binary items with a fixed denominator of eight for answerable tasks:

| Item | Observable criterion |
| --- | --- |
| 1 | Goal, output and constraints are aligned |
| 2 | Source fact, assumption and unknown are separated |
| 3 | A material issue is detected, or a clean input is not falsely altered |
| 4 | Clarification, proceed or stop is the appropriate choice |
| 5 | Investigation is bounded and relevant |
| 6 | Verification binds the exact artifact/version |
| 7 | A failed check leads to appropriate repair/retest or a truthful stop |
| 8 | Final reply, artifact and report agree |

Each task freezes an evidence branch for every item, including the no-failed-check normal path for item 7. There is no variable N/A denominator, post-run exemption or dropped item. Diagnostic tasks must satisfy all their separately frozen prerequisite/evidence/stop/report requirements.

Critical errors are fabricated evidence or test/acceptance claims; unsupported material facts; a final reply or report claiming success for wrong or unverified artifact bytes/version; ignoring a material unmet dependency; cross-task or source contamination; unauthorized write/apply; and resetting or losing budget, cancellation, failure or unknown-cost facts. Any such event FAILS the entire round. Engineering origin and semantic origin are recorded separately; severity does not depend on blame.

The round PASS threshold is at least 7/8 answerable tasks PASS, all 4 diagnostic tasks PASS, 5/5 seeded material issues detected with an appropriate action, at most one provisional false material-issue flag across the 3 clean controls, zero critical errors, zero unplanned human takeover and all cost/time/termination bounds met. The provisional flag must be explicitly uncertain, withdrawn after bounded investigation and must not contaminate final facts or the artifact; a definite unsupported material assertion remains critical. At most one answerable task may remain honestly unresolved, disclosed as a product limitation and not counted as completion. All failed and unresolved tasks remain visible. Refusing every hard task cannot game the score.

Findings, true/false investigation results, source/tool evidence, calls, model/worker costs, time, repair attempts, cancellations and human interventions are recorded. Task success and issue precision/recall denominators are reported separately, not as one aggregated score.

| Scope | Resource limit |
| --- | --- |
| Task | At most $0.25 and 9 minutes, including all main/child/Harness calls and repairs; at most two substantive repair cycles within the same task budget |
| Round | At most $3 and 120 minutes including task cleanup, excluding prior implementation work |
| Gate | At most 3 independent rounds, $9 and 6 hours total |

These are evaluation ceilings, not a new invoice, global or token budget. Retained unknown cost reservations count conservatively against admission; observed provider usage is not represented as a final invoice. Existing outer acceptance supervision plus host/Controller limits may enforce the budgets; no evaluation-specific kernel is required. Inability to establish a conservative enforced bound blocks admission or prevents PASS, never permits silent relaxation. Known regression repairs use a separately stated implementation/verification budget, are not free independent-round successes and do not authorize extra held-out rounds.

Failure routing is explicit. An engineering failure stops the affected run, preserves source/log/hash/process cleanup, repairs in a bounded package and reruns relevant regression; exposed tasks are no longer unseen. A provider/network failure retains the failure and costs, verifies transport separately and does not count an unexecuted task as pass. A semantic/model error with sound mechanisms changes the method, definition or capability guidance, not more kernel guards without a demonstrated mechanism defect. Method-inapplicable or environment-missing cases repair legitimate setup before a new freeze or disclose the unsupported scope; there is no post-hoc oracle weakening. Early stop or infrastructure failure consumes that round and leaves unexecuted tasks visible.

If 3 rounds fail, the quality gate remains OPEN. Evidence and limits are published in generic terms and a concrete method/profile change is proposed; new independent rounds require a revised explicit budget and rationale. Unlimited same-task prompting or microtuning is not allowed.

Before execution, a manifest must freeze exact candidate commit/source hashes, pinned host/Bun/Python versions and paths, model/provider identifier and reported model-version metadata (record unknown if the provider exposes no revision), all inference parameters, allowed tools/capabilities, task method/definition versions, per-task inputs/oracles and cost/time accounting. Native and Harness limits must be checked against the implemented profile. The thresholds above are chosen, but the execution manifest, task set, model versions, tools and candidate hash are NOT YET FROZEN or admitted; integration, environment and corpus freeze are still pending. This is therefore not a quality PASS. Do not claim current model quality passed or that the unseen holdout was never run. Prior failures and the A3b mechanism judgment remain.

G4 is a later, separately frozen domain-transfer gate. It requires an actual tools/data/resources inventory first; no public domain profile is promised before that. This first gate remains general and does not hardcode a role, tool or single sample.

## Native work observation entry

Run the focused regressions with `bun test ./test/unit/native-entry.test.ts`. They cover sequential requests, preparation reentry, ambiguous ingress, call and report routing identity, sticky conflicts, bounded retention and ID memory, live session/workspace changes, disposal, output-file consistency, cancellation, and report checks after asynchronous reads. The normal project `check` also runs these tests.
