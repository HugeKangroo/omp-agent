## Instanced native handoff composition

`createInstancedNativeEntry` now registers the existing main `agent_handoff` and child `agent_snapshot` factories before D1 chooses the actual main definition and tool catalog. Both tools remain `defaultInactive`; only their explicit main or child definition tool sets inside the live native ceiling can activate them. The daily entry, package flags, default strategy and OMP scheduling/execution loops are unchanged.

A task references an offer only through an exact first line `OMP_HANDOFF_REF_V1 <offerId>` starting at raw task position 0. The first line may end at LF, CRLF or CR; later lines, system prompts and other context are never scanned, and leading whitespace does not discover a reference. The entry retains the complete raw task and effective-input digest, derives the expected child prompt with the fixed two-newline `Complete assignment thoroughly:` prefix plus `task.trim().replace(/\r\n?/g, "\n")`, and requires the actual child prompt and exactly one complete user-context message to equal that derived text exactly. Observed messages are never trimmed, wrapper-stripped, joined with unrelated messages or otherwise normalized; one message containing text parts keeps its existing handling, ordinary unrelated context messages remain allowed, and interior task-text changes still refuse. A normalized parent result input remains a digest conflict, and a leading-whitespace-hidden reference remains unsupported. Canonical LF, CRLF/CR and trailing outer whitespace work; these rendering changes postdate the actual host run below and are covered by focused fixtures only. This is an internal protocol between the agent and its child tools, not a user command format. Ordinary non-handoff tasks are unaffected.

Capture returns a usable initial offer. Omitting the field preserves ordinary report behavior.

The parent task, child consumer, child tool calls and main adoption remain distinct identities. Offer reservation precedes asynchronous definition loading, one offer cannot bind twice, and failed reservations are never reused. A later lifecycle `failed` or `aborted` invalidates the consumer's handoff evidence even after a normal close, while a completed lifecycle plus normal child shutdown preserves observed evidence. Original preflight conflicts and changed effective task input are sticky. Outcomes remain condition checks with `taskAccepted:false` and `semanticAcceptance:"not-evaluated"`.

## Main handoff adapter foundation

Added `src/native-handoff-entry.ts`, an internal trusted-composition factory exporting `createNativeHandoffCoordinator` and `createNativeHandoffEntry`. It returns the main `agent_handoff` tool definition and local disposal, not an independently loadable default extension. At that increment it was not registered in the instance entry and did not include a child snapshot factory; the newer composition entry above now registers it together with that factory. One coordinator per root reuses the original core store and 64 non-evicted actual call slots. `toolCallId` is only a lookup index; the original native issued-call reference is re-verified, concurrent use of one call yields one execution, failure or cancellation is terminal for that call, and a new call is a retry. The core's tiny historical matcher is `matchesCaptureBinding(capture, work, producer)`, comparing an issued capture handle with the exact work/producer object references and adding no currentness claim.

At each effect boundary the adapter runs the prepared host refresh first, then the actual main context and `AbortSignal` reads, then the primitive identity/prepared/state pure gates, and only then file I/O or a core commit, with no host refresh after a pure gate. It rejects in-flight work on entry disposal or root close, and refuses a swapped prior reference. Replay applies a fresh scope gate but returns the original historical facts without rereading. Inputs are bounded own data with unknown fields rejected, and the same-call promise is installed before the prepare callback so reentry cannot overwrite the slot. Main operations are capture initial/repair, offer, adopt and inspect. Mutation responses are complete and bounded to 32 KiB, inspection to 256 KiB and the core view to 64 KiB; the 64×32 KiB cache allowance is separate from core budgets, not OS heap. OMP/context/lifecycle/source gates are injected ports tested with fakes, with no actual host acceptance; native preflight input-digest matching remains an A2.2 port responsibility. Registration, native identity/lifecycle/work/cancellation/preflight hooks, child `agent_snapshot` read/check, actual tool-result observation, final C2 adoption identity/file-version comparison and host closure remained unimplemented at that increment. No default entry, policy or authority changed; this is not full D3, general readiness or semantic acceptance.

## Native handoff store core (D3)

Added `src/native-handoff.ts`, a pure process-local, root-owned store for A1-issued snapshots and plans. It holds bounded capture leases, immutable versions, one-consumer offers, historical check receipts and adoptions: 4 chains, 8 captures, 1 MiB of raw text, 16 offers, 16 receipts and 16 adoptions, within 256 KiB canonical encoded metadata, 256 KiB complete prepared-read JSON responses and 64 KiB inspection; limits can only be reduced, pending reservations count against capacity, failed capture commits release their reservations atomically, and inspection reports explicit omissions. Metadata accounting counts canonical records with a shared plan once, not OS heap use or the sum of all responses. There is no I/O, model, OMP, context or host callback. The core authenticates issuance only of its own handles; supplied external root, work, producer, consumer and call references are compared by exact identity but do not authenticate their OMP source. String IDs are selectors, not permissions.

The store separates parent task binding, actual child read/check calls and the actual main adoption call. Initial conditions are fixed before capture/read as model-proposed with original proposal provenance; repair inherits the exact plan and provenance and requires a trusted adapter's actual read-result observation basis plus a valid FAIL adoption, retaining the original FAIL history. Same-call conflicting adoptions are refused across receipts, a failed checker binding cannot start a new repair, and adoption requires the latest chain head and matching live path, bytes and hash. A prepared read does not confirm delivery; result observation is a separate exact call and payload digest, conflicts are sticky, and this is not proof of model attention. Outcomes are conditions only, with `taskAccepted:false` and `semanticAcceptance:"not-evaluated"`.
