# Architecture

`omp-agent` is an OMP plugin for individual workflows. It adds explicit task ownership, bounded execution, verification, and artifact delivery while OMP retains the model and tool invocation loop.

## Components

| Component | Responsibility |
| --- | --- |
| Daily entry and host configuration | Validates one explicit workspace/input configuration and composes one task owner with execution, verification, delivery and acceptance services |
| Task owner | Maintains task identity, requirement revisions, conversation binding, and capability admission |
| Task entry | Connects actual OMP input and session events to task control |
| Execution adapter | Runs bounded Python or Bun scripts with authorized inputs and records process completion facts |
| Candidate registry | Registers execution artifacts and checks their origin, identity, size, and digest |
| Verification service | Applies host-configured contracts and trusted checks to registered candidates |
| Delivery service | Creates read-only artifact copies, requirement records, and a manifest; checks files before returning a preview |
| Acceptance service and record store | Rechecks complete host evidence, reserves task acceptance, installs a record once, and separates commit facts from current visibility and file integrity |
| Local review adapter and component | Displays frozen requirements and selected text files in the main-agent TUI, with default rejection and complete paint coverage before an explicit decision |
| Job adapter | Exercises submission, reconciliation, and cancellation semantics against an explicitly configured service |

### Explicit configured entry

The default package entry is `src/daily-entry.ts`. OMP reads `package.json#omp.extensions` when a source checkout or an extracted package directory is explicitly loaded. `src/extension.ts` remains an explicitly selected integration probe. The daily entry uses the absolute JSON path in `OMP_AGENT_CONFIG`. The JSON is the source of this entry's workspace, input whitelist, state root, optional runtime paths and human-review setting. It does not accept credentials, endpoints, model-selected paths or per-task policy overrides. Separately loaded experimental entry environment variables do not configure this composition.

The canonical workspace must match the actual OMP launch workspace. Inputs are explicit regular files outside managed internal state. Initialization validates configuration, composes one owner and one execution factory, and checks the actual persisted state and readiness audit before enabling managed calls. An existing owner is preserved rather than replaced. Partially registered handlers and tools remain inactive if initialization fails; OMP event registration is not described as reversible unregistration.

Each start creates a fresh private instance beneath the configured state root, with distinct execution, delivery and acceptance directories. Successive tasks share that instance. Prior files remain intact, but the entry does not scan them to restore task authority, candidates or history after restart.

The ready composition contributes one fixed advisory message at ordinary main-agent prompt preparation, beside the task entry's own guidance. It describes the existing workflow: establish a managed task before dependent calls, generate result files through the execution entry as registered candidates (including prose written by a task-local Python or Bun script), use only authorized input handles, verify the exact returned selection, preview delivery when a readable path is needed, and report generated, verified and accepted coverage honestly. It states that native workspace writes and shell self-tests are not managed candidates or receipts. The message is not authority, approval, automatic task creation, or native-tool enforcement; it is absent for subagents and after disposal, and it does not alter policy, budgets, human-review defaults, the native tool catalog, or shutdown behavior. Its custom type is registered as a host-owned control artifact so its own persisted transcript entry does not close the current user-turn authority window.

For evidence-based work, the same message asks the model to check unstated premises, citation support and consistency across the artifact and final reply. Direct observations remain usable; instructions, timestamps and assumptions do not establish missing events or causal links. Checks must be described within their actual coverage, and repairing a checker does not establish that unchanged content is correct. This is proportional advisory guidance: it neither requests private reasoning nor requires a long review table. Self-review and model review remain fallible advice, separate from host verification and acceptance.

The distribution includes the isolated execution launcher and the lazy human-review runtime files. Host configuration and runtime state remain outside the package. Missing configuration leaves managed handlers disabled while ordinary OMP tools remain available.

Human review is off unless the JSON explicitly contains `"humanReview": "local-main-tui-v1"`. No automatic semantic contract is installed by this entry. Insufficient verification coverage stays insufficient; final acceptance still requires the existing acceptance mechanism and its evidence. The entry preserves ordinary OMP capabilities and model selection. Its guarantees apply to managed calls, not to every native or third-party tool side effect.

## Task and execution boundaries

Task identity and requirement sources come from host-observed conversation events. Model arguments can select existing objects and provide optimistic version guards; they cannot create host authority.

A requirement amendment increments the task revision. Capabilities check that their task and revision still match before acting. Session or branch navigation can detach the task binding, preventing new mutations and execution through an outdated context.

Local execution uses host-selected paths, runtimes, input handles, time limits, and output limits. Candidates retain the source, input, and output identities needed for later checks. A process exit code alone does not establish that a task meets its requirements.

## Local history projection and archived-run evidence

Host-only modules provide bounded local history and archived-run inspection. B1 composes the history writer into the ordinary daily instance through `history-session.ts`. `agent_history` provides main-only read-only task and run queries over the current selected branch, including after OMP resumes the same session. These queries read historical associations and bounded file evidence without restoring task authority or replaying execution.

`history-entry.ts` registers `agent_history` with `approval: "read"` and `loadMode: "essential"` through the existing shared-inactive daily staging. Its runtime parser accepts `{action: "list", limit?: 1..16, cursor?}`, `{action: "inspect", selector}`, `{action: "list_runs", taskSelector, limit?: 1..16, cursor?}` and `{action: "inspect_run", runSelector}`. Only previously issued opaque selectors and cursors select records; paths, roots, instances, owner/task/run/artifact ids, revisions, sessions and permissions are never accepted as arguments. `history-view.ts` derives an instance root only from the loaded `stateRoot` plus `instances/<safe single component>`, validates real directories, canonical containment, ordinary single-link index files and stable identities, and reads only the actual `getBranch()` selected path. Each query requires the active daily composition, an actual main agent, canonical workspace, persistent session id/file, a unique continuous branch up to 4096 entries, and at most 128 locator occurrences. It never calls owner inspection or history pages, never runs an owner mutation, capture, append, `ensureOnDisk`, process probe, run, delivery or acceptance, and never writes a file.

A locator must be an exact `type=custom` / `customType=omp-agent.history.locator` entry with the eight-field B1 payload, its origin session must equal the actual session, and its complete original-plus-amendment ledger must be proven against genuine user entries strictly before that occurrence. Exact duplicates may collapse to one returned row only after each occurrence's own source prefix is checked; conflicting, malformed, unsupported, missing, changed and source-mismatched occurrences are withheld with stable reason counts and no body or selector. `list` returns bounded summaries, opaque host selectors and page coverage; `inspect` returns one complete untruncated item. Both distinguish recorded status from present execution facts, always report `historical=true`, `authorityRestored=false`, `evidence=local-record`, and leave acceptance evidence, candidate registration and run evidence unchecked; the bridge reports only its selected-branch and full-ledger checks, while A's own `branchVisibility` remains `not_checked`.

The view is one bounded metadata set bound to workspace, actual session id/file, navigation generation and the locator identity collection; it stores no task body across calls. Ordinary assistant/tool-call/tool-result appends preserve issued selectors and cursors, while an added, removed or changed locator, session/file change, navigation, disposal or current-composition replacement invalidates them and requires a new list. Every query runs the last current-composition callback before re-reading the actual branch, session identity and full source ledger, then rechecks metadata for every selected index file and parent directory. Projection contents were read earlier in the query; this final pass does not read them again. The native brand-checked abort flag is sampled only after those final host getters and metadata checks; synthetic signal objects never supply that abort fact, and the view refuses them. This is bounded observed consistency against observable mutation; it is not an atomic filesystem snapshot, adversarial transaction guarantee or protection against undetectable changes. Each A inspection is precharged 1 MiB against a 16-inspection/16 MiB nominal budget per query, with no silent truncation or extra scan to fill a page.

`list_runs` resolves an existing task selector against the real ACTIVE history row, checks its complete source ledger, and requires exactly one matching task locator before each selected run locator. It parses the entire bounded collection of at most 128 run-locator occurrences before pagination and conflict checks; malformed or unsupported entries with a bounded claimed history id remain visible as withheld diagnostics. A page evaluates at most 16 occurrences. Run selectors (`hrun_`) and cursors (`hrcur_`) use distinct namespaces and bind to the actual session-manager object, session id/file, generation, task locator and complete run collection. Run-collection changes invalidate run tokens while preserving existing task-token behavior. Ordinary message appends remain usable. Token generation uses at most four attempts and refuses a collision without overwriting an earlier binding. Listing reads task projection and branch metadata only; it does not read a run file or upgrade the locator's `byteIntegrity="not_checked"` qualifier.

`inspect_run` derives one fixed `runDirectory/record.json` location and the locator's complete artifact set from the host-issued run selector. It reserves a conservative 12 MiB allowance before the outer task-file inspection, including that inspection and the evidence checker's initial and final history, record, source, staged-input and archive reads. This is a precharge, not measured IO. All composition callbacks and actual host getters finish before the final scope, complete task/run collection, source-prefix and index-metadata checks; the synchronous evidence checker is then called once. Afterwards only pure result binding, the native abort flag and internal lifecycle state are consulted. The bridge additionally requires exact equality of the locator, requested and recorded artifact sets; the lower-level checker's subset-presence flag alone is insufficient. An empty set is valid historical data. Overall `changed`, `missing`, `mismatch`, `unsupported`, `unknown` or `incomplete` states remain explicit even when earlier individual file observations matched. Recorded process facts, current byte observations, branch checks and authority are separate fields. No raw source, log or binary contents are returned; the checker's canonical workspace fact remains present. All four actions use the same 256 KiB complete-response limit and refuse overflow without truncation.

`history-session.ts` subscribes synchronously to the daily task owner and captures only a committed `task_started`, `task_revised`, `task_cancelled` or `task_accepted` whose owner, task and revision still match the current snapshot and whose status matches the event. A `task_accepted` event must also carry the current task acceptance reference's acceptance id, delivery id, record digest and accepted time. A mismatch, ordinary prepublication projection failure or bounded-queue overflow is reported as incomplete; it never rolls back the committed owner state. A projection error explicitly coded `unknown` is distinct: publication may have happened and its read-back was not confirmed, so it is reported as `capture_unknown`/possibly applied, increments `unknown` rather than `captured` or `incomplete`, invents no history id, and disables future captures for that writer. Confirmed items enter a bounded pending queue that is deduplicated and never silently evicted.

Publication happens only from the real main-agent `agent_end` handler staged after the task-entry handler, and only when at least one captured item is pending. The component reads the actual session id, file, selected leaf and branch, waits for `ensureOnDisk` under a small local timeout, then re-reads and revalidates identity, generation and every original and amendment requirement source against the actual pre-append branch. It appends one small native `type=custom` entry with the fixed `omp-agent.history.locator` custom type and an allowlisted payload (version, instance, owner, history id, digest, task, revision and origin session). No path, root, ledger text, grant, token or run data is included, and task trusted-control types are unchanged.

`appendEntry` returns `void`, so a locator is counted visible only after the actual in-memory branch and selected leaf show exactly one new expected custom entry with a continuous parent chain. A thrown or ambiguous append is unknown/possibly applied and is never retried. Session navigation and disposal invalidate pending eligibility; a late `ensureOnDisk` completion cannot append. Projection and locator are separate writes with no transaction or fsync claim. `DailyEntryControls.history` exposes readonly pending, visible, incomplete, unknown, limit and reason diagnostics, not a history-saved boolean. Counts are cumulative observations, not a partition of unique captured items: navigation during append can report one item as incomplete and later unknown. B1 captures records; B2a adds only the bounded read-only query above. OMP owns session continuation. Neither component restores task authority or resumes execution.

The execution adapter retains at most 128 defensive run-record references totalling at most 512 KiB, each naming a single safe run-directory component derived from the prepared run, the frozen owner/task/revision/requirements identity, run and call ids, and only the artifact ids actually returned by the archive path (currently at most 8, possibly empty). A reference becomes claimable only after the final completed-format record writer returned normally and the outer execution released its busy and reservation state. That return proves only an observed host write call: references always state `recordWriteReturned=true`, `byteIntegrity="not_checked"` and `authorityRestored=false`, and never imply settlement, current bytes, candidate registration or acceptance. A writer throw or a possibly dispatched run that never reaches the final writer yields no reference; bounded diagnostics separately count final-write-unconfirmed and possibly-dispatched-without-confirmed-final-record cases, so zero references do not imply no side effects. Limit, conflict, invalid and unconfirmed counts are bounded scalars with no rejected-id collection.

B1 retains its own visible ACTIVE task-history row, including complete immutable sources, history id/digest, exact task/revision/requirements identity and original capture generation. The real main-agent `agent_end` imports the adapter snapshot after task-entry handling; task locators are published before run locators in the same attempt. A run locator is appended only when that exact task row remains in the original capture generation and exactly one exact task locator for the row is present on the actual path, with its complete original-plus-amendment source ledger proven in that locator's prefix. The same exact locator and prefix are rechecked after the run append, so mutation during the callback is unknown/possibly applied rather than visible. Task and run items share count (128) and byte reservations, run payloads reserve their 4096-byte ceiling before append, and a bounded latch refuses all unseen run keys once key capacity is exhausted instead of forgetting and later accepting them. The native `omp-agent.history.run-locator` version 1 payload is at most 4096 UTF-8 bytes and excludes paths beyond the single run component, source bodies, logs, process ids, grants, tokens and model conclusions. Navigation, disposal, timeout, missing or changed locators, wrong sessions, source mismatch, duplicate or conflicting imports and ambiguous appends are refused or counted separately from task capture; consumed/refused/unknown run keys are bounded and never retried. This is linkage metadata only: it performs no process probe, replay, registry restoration, run/artifact query or authority mutation.

`history-projection.ts` captures one explicitly supplied committed `ManagedTask` into a fixed `history-index.json` directly beneath an existing host-selected private instance root. The versioned file has a fixed header and append-only rows. It stores task identity, revision, recorded status and times, four creation-anchor fields, the complete requirement-source ledger with its existing digest, and an acceptance reference. It excludes active grants, tokens, capabilities, budgets, model understanding and process-control state. Limits are 128 rows, 16 rows per list page, 128 KiB per projected item and 1 MiB for the whole file; overflow is refused before writing and old rows are never silently evicted. A writer creates only its own new index using fully written and checked temporary bytes plus atomic publication, and never adopts a pre-existing unknown index. Reads re-read the actual file and return defensive copies. A local record and its digest prove local content consistency only; they are not signatures, current authority, branch visibility or acceptance evidence.

`history-evidence.ts` accepts an explicit instance, an inspected history-item selector and a relative run-record locator. It re-reads the actual run record under that instance's execution root, the recorded script source, all staged inputs and only the caller-selected archived artifacts. Owner, task, revision, requirements digest, run id and call id must all match. Every selected artifact id must be unique and present with its recorded relative path, byte count and digest; unselected intermediate artifacts are not required. File reads are bounded and checked before and after for path containment, directory/file type, link count, identity, size, timestamps and digest. Results separate metadata association, observed byte integrity, recorded process facts and current process state. A completed record never proves the current process state; recorded PIDs are display-only historical values. This path does not probe or signal processes, register candidates, run verification, check delivery or acceptance, restore a grant, or claim branch visibility. Missing, unsupported, changed, mismatched and unknown states are reported explicitly. A failure after history publication is reported as possibly applied, never as confirmed capture.

## Verification and delivery

A verification contract is bound by the host. The model cannot select a weaker verifier, change thresholds, or supply its own successful receipt. Verification reports pass, fail, or insufficient coverage and retains condition-level evidence.

Delivery selects registered candidates from a particular run. The service checks the original evidence, creates separate read-only files, and checks the copied bytes. A delivery includes the requirement sources and a manifest. Repeated requests check the existing files before returning the same bundle.

Delivery preview and final task acceptance are distinct. The experimental model interface supports verification, preview, submission, and accepted-file inspection. Submission selects an existing delivery and task revision; it cannot supply a receipt, verdict, confirmation flag, or arbitrary path. An explicitly configured acceptance service rechecks complete semantic coverage, a matching current pass receipt, task revision, and actual file identities. It installs a record without replacing an existing target before transitioning the owner to accepted. Late notification or maintenance failures cannot reverse a completed commit; an uncertain outcome remains unknown and blocks further mutation.

The record-store port comes from the actual task owner and is captured once by the acceptance service. This preserves the issuing store across OMP entry factories and imported modules. Record installation remains a fixed owner operation.

Submission and inspection return bounded JSON in model-visible tool content. Operation commitment, current task visibility, historical acceptance, and file integrity have separate fields. Read-only inspection creates no new acceptance. Later damage does not erase historical acceptance, and a successful preview alone does not imply acceptance.

Late cancellation, revision, or execution cannot reopen an accepted task. A context change, abort, or disposal during a call can withhold current information and file paths while preserving the original operation result. Historical execution and verification records retain the facts recorded when they were created.

## Optional human review mechanism

The host mechanism for human review is default-off and uses the same task owner, acceptance reservation, record-store port, and fixed commit path. A review prepares a complete bounded display of the current requirements and selected UTF-8 delivery files. The original bytes and display digest are bound separately. The deadline includes preparation and waiting; cancellation, revision, context loss, or file changes invalidate the pending review.

Human and hybrid records use an explicit v2 schema. Automatic acceptance continues to write v1 records. A valid partial automatic check retains its original insufficient outcome; a human decision may supplement uncovered semantics, but cannot override a failed or invalid configured check. Private verification issuance facts distinguish valid partial evidence from malformed verifier results without changing the historical receipt or model-visible verification result.

The fixed local adapter uses OMP public custom UI and terminal helpers. The experimental entry enables it only with the exact `OMP_AGENT_HUMAN_REVIEW=local-main-tui-v1` setting and configured delivery and acceptance directories. The model can request review of an existing delivery with exact task guards; it cannot approve. Only the current main-agent TUI context can display a review.

The component defaults to Reject and counts matching completed paints rather than render calls alone. Resizing resets page coverage and selection; pasted input cannot approve. Task or context changes, cancellation, the fixed five-minute deadline, and disposal invalidate a pending review. TAB and control characters are escaped for display while original file bytes remain independently bound.

The documented native integration scenarios passed using automated terminal input, including the actual fixed deadline. Genuine human review is pending. Simulated transport and automated terminal input are engineering evidence, not a human decision.

## Current limits

Candidate and delivery registries are process-local. The project does not yet provide cross-process task recovery, a production job backend, or a formally released version. Filesystem checks describe the observed local state and do not claim transaction isolation against arbitrary external processes.
